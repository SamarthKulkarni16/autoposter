# 2026-09-01 — Facebook Reel flow: major progress, one remaining blocker

## CONTEXT
Picked up from 2026-08-31: Facebook Reel blocked on "video upload doesn't
register" (all composer file inputs ended at files.length=0) and then "Next
never becomes enabled".

## WHAT I FIXED (all code-level blockers cleared) — committed 2f565f8

1. **UPLOAD — use the REAL file chooser, not synthetic events.**
   - The reliable method (proven live): JS-click "Add Video" inside
     `page.expect_file_chooser()` then `chooser.set_files(path)`.
   - Synthetic DataTransfer drag-drop onto the <form> only sometimes clears
     the placeholder and never reliably enables Next → abandoned.
   - `set_input_files` on an accept-matching hidden input doesn't fire
     Facebook's change listener (it binds to the visible Reel input the
     "Add Video" button opens) → fallback only.
   - Rewrote `_upload_reel_video` to: fresh composer per retry, chooser
     first, set_input_files on the Reel video input as fallback.

2. **Next handling — `engine.wait_for_enabled` now returns the ENABLED
   match, not `.first`.**  The Reel screen can have a stale/disabled Next (the
   wall "What's on your mind / Add to your post / Next") PLUS the live enabled
   Reel Next. `.first` locked onto the disabled one forever. Now scans all
   matches for an enabled+visible one.

3. **Title field — `engine.fill_contenteditable`.**  The Reel title is a
   Lexical contenteditable whose inner <p> "subtree intercepts pointer
   events", so Playwright's strict click on it loops forever. Fix: JS-focus
   the element, then keyboard Ctrl+A/Backspace + type.

4. **Public check — `_ensure_public`.**  Was failing to detect "Public"
   because `get_by_text("Public").first` hit a hidden/non-element node. Now
   checks the audience button (name "Public / Anyone on or off Facebook") and
   any VISIBLE "Public"; defaults to Public already-selected.

5. **Post — wait for it to enable (disabled = upload rejected), then
   JS-click** (avoid pointer-intercept). Confirmation waits for composer close
   / "reel has been published" banner (the old "Your reel was posted" guess
   never matched).

## PROOF THE FLOW WORKS
`debug/fb_postreal_diag.py` (removed after use) drove the WHOLE flow with the
real chooser upload and **published an actual Reel**: composer opened → upload
→ Next → Next → title → Public → Post → "your reel has been published". So the
sequence and all selectors are correct.

## REMAINING BLOCKER — Facebook rejecting the video uploads right now
- After a burst of ~20 rapid test uploads, every upload now gets a visible
  "your file can't be uploaded: hi.mp4" toast ~6s in, and **Post stays disabled**
  (the flow reaches the details screen then 'Post' never enables).
- Happens for the throwaway blue clip AND the real 12.6MB Pinterest video (which
  posts fine to Pinterest), and a FB Reel posted identically at ~06:39 earlier
  today. So it is NOT a codec bug:
  - `MediaSource.isTypeSupported('video/mp4; codecs="avc1.4d401f"')` = true,
  - `canPlayType('video/mp4; codecs="avc1.4d401f"')` = 'probably' on the snap
    chromium used.
- Conclusion: **Facebook-side rejection / anti-abuse / rate-limiting** triggered
  by hammering the composer with repeated identical uploads. Needs a cooldown
  (minutes) and then a SINGLE clean run, ideally with real varied content, or
  manual verification that the account isn't temporarily restricted.

## IMPORTANT TRAP I HIT (don't repeat)
Scanning raw `body.inner_text()` for "can't be uploaded" is a false-positive
trap: once a reject toast appears it can persist in the DOM as hidden text and
make every later check instantly reject. Base registration/success on the
VISIBLE actionable state (Next enabled / placeholder in the live composer),
not raw body substring scans.
